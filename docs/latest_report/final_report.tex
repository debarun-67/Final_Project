\begin{abstract}
\fontsize{11pt}{11pt}\selectfont

This report details the architecture and implementation of a permissioned blockchain designed specifically to ensure the integrity of electronic medical records. By employing a hybrid storage model, the system stores sensitive clinical data securely off-chain while anchoring cryptographic hashes, metadata, and validator identities on an immutable ledger. Rather than replacing existing Electronic Health Record (EHR) databases, this architecture functions as a tamper-evident audit layer capable of cryptographically proving a record's immutability from the moment of registration.

The implementation extends significantly beyond a foundational Proof-of-Authority (PoA) C-based core, realizing a full-stack distributed system. The current framework integrates a native C ledger engine, a Node.js/Express API middleware, and a Vite/React frontend dashboard. The core engine autonomously handles block and transaction structures, Merkle proof generation, peer-to-peer TCP networking, state synchronization, and O(1) duplicate record detection. Operating as the integration layer, the API bridge surfaces network diagnostics and facilitates proof-backed file verification, while the React frontend exposes role-based interfaces for administrators, clinicians, and patients.

Targeting consortium healthcare networks comprising known institutional actors, the system discards the computational overhead of Proof-of-Work in favor of a PoA consensus model. The network relies on a synchronous, three-phase-commit-inspired voting sequence (CAN\_COMMIT to DO\_COMMIT) to achieve deterministic finality with minimal latency. 

The primary contribution of this work is the end-to-end integration of a bare-metal ledger with a modern clinical web interface. Unlike conventional prototypes that remain confined to smart-contract theory or command-line utilities, this system bridges low-level socket networking with browser-side Merkle verification. While currently operating with mock demonstration signatures and zero-dependency authentication to facilitate rapid evaluation, the underlying cryptographic logic is fully functional. The integration of AES-256-GCM encryption, production-grade ECDSA key management, and robust transport layer security remains the designated trajectory for transitioning this prototype into compliance-ready hospital infrastructure.


\vspace{1cm}\noindent\textbf{Keywords:} Permissioned Blockchain, Proof of Authority, Electronic Health Records (EHR), Merkle Trees, Cryptographic Key Management, Browser-Side Merkle Verification, Off-chain Storage, Decentralized Healthcare.
\end{abstract}

\section{INTRODUCTION}

\subsection{Background}

Healthcare data represents a uniquely sensitive class of digital information. A single clinical record aggregates a patient's diagnostic history, surgical notes, imaging results, and long-term identifiers. The absolute correctness of this data is a direct prerequisite for patient safety. When clinical records are altered, forged, or silently deleted, the fallout extends beyond administrative confusion and directly jeopardizes medical decision-making.

Contemporary healthcare institutions rely predominantly on centralized Electronic Health Record (EHR) systems. While highly optimized for storage efficiency and rapid retrieval, these architectures consolidate trust within a single administrative domain or privileged operator group. If this centralized node is compromised, both the historical record and its corresponding audit trail lose their reliability. A malicious insider, a compromised credential, or a targeted ransomware attack can silently alter patient histories while simultaneously erasing the forensic evidence of that manipulation.

Distributed ledger technology offers a structural alternative to this centralized vulnerability. By maintaining an append-only sequence of cryptographically linked blocks, a blockchain ensures that any historical modification alters the subsequent hash chain, rendering tampering mathematically evident. However, deploying blockchain in healthcare introduces severe privacy constraints; raw medical data cannot be broadcast across a decentralized network. Consequently, this system implements a strict hybrid architecture. It encrypts and sequesters the sensitive files off-chain within the local hospital node, writing only the deterministic file hashes and lightweight metadata to the distributed ledger as an immutable integrity anchor.

Crucially, this architecture avoids the abstraction layers of established networks like Ethereum or Hyperledger Fabric. Engineered as a custom, native implementation, it exposes the underlying mechanics of decentralized consensus. Block creation, SHA-256 hash chaining, raw socket networking, and disk persistence are managed directly at the systems level, providing a transparent, full-stack prototype that bridges low-level C execution with modern web presentation.

\subsection{Problem Statement}

The primary research question addressed by this work is:

\textit{How can a healthcare consortium maintain a tamper-evident, auditable, and distributed ledger of medical file integrity without exposing sensitive protected health information directly on a blockchain?}

This challenge decomposes into the following specific engineering problems:

 Representing medical files on-chain without exposing the underlying plaintext., Cryptographically securing the block history against undetected modification., Establishing validator identity within a permissioned, non-anonymous network., Detecting duplicate transactions and replayed file hashes in constant time., Synchronizing ledger state across disparate local nodes., Bridging the native C ledger to a high-level web middleware., Providing role-specific graphical interfaces for administrators, clinicians, and patients., and Identifying critical security limitations requiring resolution prior to clinical deployment..

This project resolves these questions at the prototype level, proving the viability of the core ledger and consensus logic while clearly defining the boundaries for future production hardening.

\subsection{Objectives and Scope}

The central objective is the end-to-end engineering of a custom blockchain core dedicated solely to medical record integrity. This necessitates off-chain payload encryption coupled with on-chain SHA-256 hash anchoring. The system design requires validator identity management, local binary disk persistence, and a robust peer-to-peer TCP synchronization protocol. Secondary objectives involve the implementation of a Bloom-filter-based duplicate detection mechanism, the deployment of a Node.js API bridge, and the construction of a React-driven operational dashboard.

The scope of this implementation is strictly confined to data integrity. The architecture does not attempt to replicate the vast data management capabilities of a comprehensive EHR, nor does it seek to automate complex clinical billing workflows. It functions explicitly as a tamper-evident audit layer designed to operate in parallel with existing hospital infrastructure, ensuring that once a record is registered, its historical immutability can be mathematically proven.

\section{COMPARATIVE EVALUATION}

\subsection{Centralized Architectures and Distributed Alternatives}

The transition to Electronic Health Records (EHRs) has improved clinical coordination, but the reliance on centralized relational databases introduces structural vulnerabilities. Centralized EHRs inherently constitute single points of failure, rendering them susceptible to network outages, ransomware, and insider manipulation~\cite{1}. Because the entity storing the medical records typically also manages the audit logs, a compromised administrative credential allows an attacker to alter diagnostic histories while simultaneously erasing the forensic evidence.

To mitigate these vulnerabilities, the medical informatics community has explored distributed ledger technologies (DLTs)~\cite{5}. Blockchains provide cryptographic provenance and tamper-evidence without a central administrator. However, deploying public blockchains (e.g., Ethereum) in healthcare environments introduces operational limitations, including high transaction costs, network latency, and conflicts with privacy regulations such as HIPAA and GDPR~\cite{5}.

This section contextualizes the proposed permissioned blockchain architecture against contemporary decentralized healthcare frameworks. By examining the technical and cryptographic paradigms of legacy systems, we highlight persistent industry limitations and demonstrate how the proposed C-based ledger, coupled with its web middleware, addresses these challenges.

\subsection{Architectural Comparison}

The proposed architecture departs from the abstractions of enterprise frameworks like Hyperledger Fabric and public smart-contract networks. It is structured across three operational layers:

 \textbf{Native C Blockchain Core:} Bypassing virtual machines, the core manages fixed-size C structures for blocks and transactions. It handles SHA-256 hashing, Merkle root verification, raw TCP socket networking, and binary storage via a \texttt{blockchain.dat} file. Disk synchronization (using \texttt{fsync} or \texttt{\_commit}) guarantees data durability., \textbf{API Middleware:} A Node.js and Express bridge translates between the native C binaries and web clients, serializing data into JSON, aggregating system logs, and providing local authentication., and \textbf{Frontend Dashboard:} A React/TypeScript application provides role-based interfaces for administrators, clinicians, and patients, facilitating block exploration and file verification workflows..

Crucially, the system enforces a hybrid storage paradigm. Protected health information (PHI) is encrypted (currently via a mock envelope sequence, intended for AES-256-GCM) and stored securely off-chain in a local directory. The blockchain stores only a lightweight metadata payload containing the patient ID, doctor ID, off-chain pointer, timestamp, and the SHA-256 hash of the plaintext document (computed before encryption).

\subsection{Addressing Insider Threats and Centralized Failures}

Centralized EHR architectures consolidate patient data onto a single server, creating high-value targets for attackers~\cite{1}. Furthermore, the digitization of records exposes them to privilege abuse by malicious insiders. While previous work has proposed anomaly detection using Support Vector Machines~\cite{11} or multi-tiered Role-Based Access Control (RBAC)~\cite{1}, these methods often fail to prevent unauthorized data duplication. Federated learning frameworks, such as APPDFL~\cite{12}, attempt to decentralize threat detection but remain vulnerable to data poisoning if the training data provenance is not cryptographically anchored~\cite{14, 16}.

The proposed architecture addresses these failures through deterministic cryptographic immutability rather than probabilistic anomaly detection~\cite{3}. The peer-to-peer network employs a synchronous, three-phase-commit-inspired (3PC) flow (CAN\_COMMIT, VOTE\_YES, PRE\_COMMIT, ACK\_PRE, DO\_COMMIT) to reach consensus. If an insider modifies a raw file in the off-chain directory, the file's SHA-256 hash immediately diverges from the immutable on-chain record, mathematically exposing the tampering.

\subsection{Overcoming EVM Constraints and Public Blockchain Bottlenecks}

Early blockchain healthcare research, notably MedRec~\cite{18}, utilized Ethereum smart contracts for access control, incentivizing medical researchers to act as ``miners''~\cite{19}. However, transaction latency and variable gas fees render public Proof-of-Work (PoW) networks unviable for high-throughput clinical environments~\cite{9, 20}. Cost-optimization on the Ethereum Virtual Machine (EVM) forces developers into unnatural paradigms, such as variable packing and avoiding dynamic arrays, leading to network congestion and system fragility~\cite{5}. While Layer-2 rollups reduce costs, they introduce secondary complexities regarding data availability~\cite{8}.

By utilizing a custom-built, native C blockchain core within a permissioned consortium, the proposed architecture circumvents EVM constraints and gas markets. Deterministic memory allocation using fixed-width C structs eliminates garbage collection overhead, enabling fast append operations suitable for hospital networks without the unpredictable costs of public blockchains.

\subsection{Semantic Interoperability and Smart Contract Decoupling}

Frameworks like Ancile~\cite{22} use Ethereum smart contracts for highly granular access control, inheriting computational bloat~\cite{23}. Similarly, FHIRChain~\cite{25} attempted to encapsulate HL7 FHIR data models directly within the blockchain. Forcing deeply nested FHIR JSON objects or integrating Large Language Models (e.g., ClinicalBERT) into on-chain state variables introduces significant parsing overhead~\cite{27, 29}.

The proposed system deliberately decouples complex business logic from the blockchain. The on-chain footprint is aggressively lightweight, storing only foundational metadata. Semantic interoperability, RBAC, and session management are handled entirely by the Express API and React frontend, ensuring horizontal scalability without requiring hard forks of the consensus rules.

\subsection{The Hybrid Storage Dilemma}

Storing raw medical data on-chain violates the right to erasure and drastically inflates ledger size. Consequently, hybrid paradigms are the industry standard. MeDShare~\cite{31} utilized cloud repositories (e.g., AWS) while using the blockchain for provenance~\cite{33}, maintaining a dependency on corporate infrastructure. OmniPHR~\cite{34} and frameworks for radiation oncology~\cite{36} proposed distributed routing or symmetric key retrieval. 

More recently, IPFS has become common for off-chain storage~\cite{38, 40}. However, IPFS is an ephemeral swarm; unpinned files can be lost to garbage collection~\cite{43}, and retrieving large clinical files introduces unpredictable latency~\cite{45}.

The proposed system bypasses IPFS latency and data-loss risks through deterministic local off-chain storage. Encrypted payloads are committed directly to a dedicated local directory, guaranteeing high availability and predictable retrieval speeds on controlled, HIPAA-compliant hospital infrastructure.

\subsection{Consensus Evolution: Proof of Authority}

The environmental waste of PoW led to alternatives like Delegated Proof of Stake (DPoS) in MedBlock~\cite{47}. However, stake-based systems introduce tokenomics inappropriate for a hospital consortium. Consequently, Proof of Authority (PoA)—relying on the verified identity of pre-approved validators—has emerged as the optimal consensus mechanism for healthcare~\cite{49, 52, 53}.

The proposed system implements a custom 3PC PoA protocol over raw TCP sockets. Validators verify the Merkle root, hash linkage, and signatures before voting. This synchronous mechanism provides a demo voting-based finality without mining waste or heavy infrastructural requirements. In the current prototype, the quorum threshold is hard-coded and peer messages are not cryptographically signed.

\subsection{Duplicate Detection via Bloom Filters}

Duplicate medical records fragment patient histories and cause clinical errors~\cite{55}. Traditional Master Data Management (MDM) frameworks~\cite{57, 59} rely on computationally expensive probabilistic semantic matching. 

In contrast, the proposed architecture uses a pure-C Bloom filter with three independent DJB2-based hash functions for constant-time $\mathcal{O}(1)$ pre-filtering. If the hash triggers a match, an in-memory hash map confirms the duplication, and the API rejects the upload before it reaches the blockchain. A proposed LevelDB integration would allow scaling this detection to over a billion records with minimal RAM usage.

\subsection{Browser-Side Merkle Inclusion Verification}

Many web-based blockchain dashboards introduce a light-client trust boundary: if the backend API is compromised, it can spoof validity responses. The proposed project addresses this by implementing browser-side Merkle inclusion verification.

When a file is verified, the API returns a Merkle proof and block header metadata. The React frontend independently recomputes the SHA-256 hash of the uploaded file, reconstructs the transaction leaf, mathematically applies the sibling hashes, and verifies that the computed root matches the block header's Merkle root. This ensures true end-to-end integrity verification, immune to API-level spoofing.

\section{PROPOSED SYSTEM}

\subsection{System Overview}

The project is a full stack prototype of a permissioned medical blockchain system. It has three primary components.

\subsection{C Blockchain Core}

The C core is located mainly under:

backend/core/src

It defines the block and transaction structures, computes SHA-256 hashes, stores blocks in a local binary ledger file, provides a viewer tool, validates the chain, and runs networked node instances. It also stores key files and off-chain encrypted record files under the core directory or demo instance folders.

\subsection{Express API}

The API is located under:

backend/api

It uses Node.js and Express. Its role is to expose blockchain information to the frontend. It runs the C viewer binary through child processes, parses the text output, and returns JSON. It also scans node ports to report network health and reads log files from demo node instances.

\subsection{React Frontend}

The frontend is located under:

frontend

It is a Vite React TypeScript application. It provides pages for:

 Login, Dashboard, Block Explorer, Network Health, System Logs, Upload Record, My Records / All Records, Verify Record, Patient Search, Activity Logs, and Settings.

The frontend gives the project an operational face. Instead of only being a command-line blockchain, the project can be demonstrated as a hospital-style web dashboard.

3.3.1 C Blockchain Core

The C core is the foundation of the system.

3.3.1.1 Main Data Structures

The fundamental \texttt{Transaction} structure is strictly defined to capture the minimal necessary metadata, comprising the patient and doctor identifiers, the cryptographic hash of the medical data payload, a pointer to the off-chain storage location, and an immutable timestamp.

3.3.1.2 Hashing

The system utilizes a standalone SHA-256 implementation written natively in C, serving as the foundational cryptographic primitive across the network. This algorithm is universally applied for hashing arbitrary text data, verifying raw file contents, computing transaction identifiers, constructing Merkle trees, and generating definitive block hashes.

The block hash is deterministically computed by concatenating the block index, creation timestamp, previous block hash, and the transaction Merkle root.

The Merkle root is computed from transaction fields. This means that if a transaction changes, the Merkle root changes, and therefore the block hash changes.

3.3.1.3 Genesis Block

The chain begins with a genesis block. The current implementation uses a fixed timestamp and a universal genesis validator port of 8001. The genesis transaction uses patient\_id = GENESIS and doctor\_id = NETWORK. This creates a predictable starting point for all nodes.

3.3.1.4 Persistence

Blocks are appended to a binary file:

data/blockchain.dat

The \texttt{add\_block} function enforces immediate persistence by writing the block, flushing the stream, and invoking explicit OS-level synchronization commands—specifically \texttt{\_commit} on Windows and \texttt{fsync} on Unix-like environments.

This is good because it reduces the risk of data remaining only in memory after a write.

3.3.1.5 Verification

The core ledger engine enforces strict validation rules before appending any block. It independently verifies the cryptographic correctness of the block hash, validates the expected signature payload, ensures proper linkage to the preceding block\'s hash, and rejects any duplicate transaction hashes either within the proposed block itself or against the historically committed chain.

Full chain verification reads blocks sequentially and checks that each block points to the previous stored hash.

3.3.1.6 Duplicate Detection

The project includes a transaction hash index implemented as a hash map with chained linked lists. The index stores the transaction data\_hash together with the block index and transaction index. This improves duplicate lookup compared to scanning the whole chain every time and also supports proof lookup for VERIFY\_FILE. Recent corrections clear the index when the blockchain file path changes, which matters because demo nodes may use different ledger files. In production this index should be persistent and stored in a database, but clients must still verify returned proofs rather than trusting the index server blindly.

3.3.1.7 Viewer Tool

The viewer binary exposes a robust administrative interface, providing essential commands such as \texttt{HEIGHT}, \texttt{LAST}, \texttt{ALL}, \texttt{VERIFY}, \texttt{VERIFY\_FILE}, and \texttt{ADD}.

VERIFY\_FILE now returns a proof-backed response for a matching file. It recomputes the uploaded file hash, looks up the transaction location through the in-memory hash index, loads the relevant block, generates a Merkle proof, verifies the proof against the block Merkle root inside the C core, and prints header, transaction, and proof fields for the API layer to parse.
It also supports precise block inspection via the \texttt{PRINT <index>} command.

The Express API depends heavily on this viewer output. It parses the text format and converts it to JSON for the frontend.

3.3.1.8 Key Generator and Key Management Architecture

The current implementation splits key creation and management into two paths:

1. Validator Keys: Created via the dedicated helper utility generate\_keys.c. Running this program generates mock public and private key files on disk (e.g., keys/\{port\}\_private.pem and keys/\{port\}\_public.pem). In a production blockchain network, validators would generate real RSA-4096 or ECDSA private keys locally, submitting the corresponding public keys to the consortium authority for inclusion in the authorized validator set.
2. Patient and Doctor Keys: In this prototype version, no standalone cryptographic key files are generated for end-users. Instead, their unique database identifiers (such as PAT\_001 or DOC\_001) act directly as their public keys. The backend API maps the user's authenticated session to these identifiers, which are then used as parameters for the C core's XOR-based mock envelope encryption. In a production environment, this is replaced by client-side keypairs stored in device hardware enclaves.

3.3.2 Network and Consensus Layer

The network layer is implemented in C using TCP sockets. It supports both Windows and Unix-like environments through conditional compilation.

3.3.2.1 Peer Connections

Each node starts a server socket and accepts incoming peer connections. It can also connect to peer ports passed through the command line. Nodes identify themselves using MY\_PORT messages.

3.3.2.2 Synchronization

The peer synchronization flow initiates when a node exchanges its current \texttt{CHAIN\_HEIGHT} with a peer. If a discrepancy is detected, the lagging node issues a \texttt{GET\_BLOCK} request for the specific missing indices. The peer responds with \texttt{SYNC\_BLOCK} messages containing the serialized data, which the receiving node rigorously deserializes, cryptographically verifies, and appends to its local ledger.

This design allows a lagging node to catch up from peers.

3.3.2.3 Three-Phase-Commit-Inspired Flow

The network employs a custom consensus protocol heavily inspired by the Three-Phase Commit algorithm. A proposing validator creates a block and broadcasts a \texttt{CAN\_COMMIT} message containing the serialized block data. Peer nodes independently verify the block and respond with a \texttt{VOTE\_YES} message if it meets all consensus rules. Upon accumulating a sufficient threshold of unique peer votes, the proposer transitions to the next phase by issuing a \texttt{PRE\_COMMIT} command. Peers acknowledge this phase shift with an \texttt{ACK\_PRE} message. Once the proposer receives the requisite acknowledgments, it permanently appends the block to its local ledger and broadcasts a final \texttt{DO\_COMMIT} directive, instructing all peers to finalize the append operation on their respective ledgers.

3.3.2.4 Current Consensus Strength

This is a useful prototype consensus workflow. It shows that peers do not blindly accept any block. They validate and vote. It also avoids accepting duplicate votes through a vote mask.

3.3.2.5 Current Consensus Limitations

The current consensus is not production Byzantine fault tolerant. It assumes mostly honest nodes. It does not solve all cases of network partition, equivocation, malicious proposer behavior, view change, validator slashing, or formal leader election. The majority threshold is currently coded around a small demo network. A production system would need a configurable validator set and formal quorum rules.

3.3.3 Backend API Bridge

The backend API is a Node.js/Express service.

3.3.3.1 Purpose

The API exists because the frontend cannot directly read binary blockchain files or execute C programs safely. The API acts as a bridge between browser and core.

3.3.3.2 Main Routes

The blockchain routes include:

 GET /api/height, GET /api/blocks, GET /api/block/:index, and GET /api/verify.

The network routes include GET /api/network/health and GET /api/network/logs.

The record route includes:

 POST /api/records/upload.

3.3.3.3 Core Bridge

The API runs the C viewer executable through child\_process.exec. It first attempts to run commands from a live demo node directory, especially demo\_instances/node1. It then parses viewer output.

This approach is simple and effective for a demo. It also keeps the C core separate from the JavaScript server. However, it is not ideal for production because child process execution is slower and riskier than a structured native interface, RPC service, or database-backed bridge.

3.3.3.4 Parser

The parser reads lines such as:

It converts them into JSON blocks with nested transactions.

3.3.3.5 Network Health

The network health controller scans ports 8001 through 8010 on localhost. Any port accepting a TCP connection is treated as an online node. This is practical for the local demo and dashboard. For production, node discovery should come from a signed registry or service discovery layer rather than port scanning.

3.3.3.6 Logs

The API reads:

 backend API server logs and demo\_instances/node*/data/network.log.

It aggregates these logs for the frontend System Logs page.

3.3.3.7 Authentication

The backend and frontend authentication models have been unified around a robust, zero-dependency local mock authentication system. The backend middleware validates the X-Mock-User-ID header against an internal mock user registry. This removes the integration gap that previously existed when mixing local frontend state with external Supabase dependencies, ensuring a fully self-contained local demonstration.

3.3.4 Frontend Dashboard

The frontend is a React TypeScript dashboard.

3.3.4.1 Main User Roles

The application distinguishes between patient, doctor, and admin roles.

Each role sees different sidebar links and allowed pages.

3.3.4.2 Dashboard

The dashboard displays the chain height, network status, active node count, and recent blocks.

This gives a quick operational overview.

3.3.4.3 Block Explorer

The block explorer displays blocks, hashes, previous hashes, Merkle roots, validator ports, transaction count, and metadata. It also includes a "Verify Full Chain" action that calls the backend verification route.

3.3.4.4 Network Health

The network page displays online validator nodes, ports, type, status, and latency. It is useful for showing that the blockchain is not only a data structure but a distributed network.

3.3.4.5 System Logs

The system logs page merges API logs and node logs. This supports audit and debugging.

3.3.4.6 Upload Record

The upload page lets a doctor or admin enter:

 patient ID, doctor ID, encryption password, and medical file.

It sends the file through FormData to the /api/records/upload endpoint. The backend calls the C core ENCRYPT command to securely encrypt the record under the doctor's and patient's key envelopes, saving the resulting .enc file in the demo node's offchain/records directory. It then calls the C core's ADD command with the file path, data pointer, patient\_id, doctor\_id, and validator port. On success, the frontend displays the committed block index, SHA-256 hash, data pointer, patient ID, and doctor ID returned by the core. Duplicate file submissions are detected and rejected with a 409 response.

3.3.4.7 My Records

The records page reads blockchain blocks and extracts transactions. If the user is a patient, it filters records by patient\_id. Admins can see all records.

3.3.4.8 Verify Record

The verify page uploads the file to /api/records/verify. The backend passes the file to the C viewer VERIFY\_FILE command. The C core recomputes the SHA-256 hash of the uploaded file, uses the transaction hash index to locate the block index and transaction index, and generates a Merkle proof for the matching transaction. If a matching data\_hash is found, the response includes the block index, transaction index, record hash, data pointer, patient ID, doctor ID, transaction metadata, block header fields, Merkle proof leaf, proof length, computed root, and each sibling proof step with left/right direction.

The frontend no longer treats the backend's MATCH response as sufficient by itself. It recomputes SHA-256 over the uploaded file in the browser, reconstructs the canonical transaction leaf from returned metadata, applies the Merkle proof step by step, compares the computed root with the block header Merkle root, and recomputes the block hash from the returned header fields. The page displays success only if the local proof check succeeds. If no match is found, the computed hash is shown alongside a clear failure message.

3.3.4.9 Activity Logs

The activity logs page converts block and transaction history into audit events such as BLOCK\_SIGNED and RECORD\_UPLOAD.

3.3.4.10 Settings

The settings page is mostly a static UI placeholder for profile, security, notifications, storage configuration, and public key display.

3.3.5 Data Model and Storage Design

3.3.5.1 On-Chain Data

The chain stores:

 block index, block timestamp, previous block hash, block hash, Merkle root, validator signature, validator port, and transaction array.

Each transaction stores:

 patient\_id, doctor\_id, data\_hash, data\_pointer, and timestamp.

3.3.5.2 Off-Chain Data

Encrypted medical files are stored in offchain/records folders. The data\_pointer field points to these files. The blockchain does not need the file contents to preserve integrity; it only needs the file hash.

3.3.5.3 Why Hybrid Storage Is Important

If raw medical files were stored directly on-chain:

 every node would store patient data, deletion would become extremely difficult, privacy exposure would increase, chain size would grow rapidly, and compliance concerns would become serious.

With hybrid storage:

 the chain remains lightweight, private files remain outside the ledger, file integrity can still be verified, and deletion or access revocation is more realistic.

3.3.5.4 Merkle Root

The Merkle root summarizes all transactions in a block. If a transaction changes, the Merkle root changes. Since the block hash includes the Merkle root, transaction tampering changes the block hash and breaks verification.

3.3.5.5 Merkle Proof Verification

The implementation now supports proof-backed record verification. A Merkle proof contains the transaction leaf hash, each sibling hash needed to climb from the leaf to the root, and the left/right position of every sibling. This allows a lightweight client to verify record inclusion using the uploaded file, transaction metadata, proof path, and block header instead of downloading the full block.

The current frontend performs this proof reconstruction in the browser. This provides inclusion verification, but production SPV security also requires validation that the returned block header is part of the authorized chain.

3.3.6 Transaction Lifecycle

The ideal transaction lifecycle is:

1. Doctor selects a medical file.
2. System encrypts or receives an encrypted file.
3. System computes SHA-256 hash of the plaintext file (before encryption, so the anchor is content-addressed).
4. System creates a transaction containing patient\_id, doctor\_id, data\_hash, pointer, and timestamp.
5. Node checks whether data\_hash already exists.
6. Node creates a block.
7. Node computes Merkle root.
8. Node computes block hash.
9. Validator signs the block hash.
10. Node broadcasts CAN\_COMMIT.
11. Peers verify block.
12. Peers vote yes if valid.
13. Proposer sends PRE\_COMMIT.
14. Peers acknowledge.
15. Proposer and peers commit the block.
16. Frontend dashboard displays the new block and record.
17. Later, a verifier recomputes the file hash and compares it to the stored hash.

\subsection{Advantages over Existing Systems}

The proposed Permissioned Blockchain-Based Medical Record Integrity System intentionally strips away the unnecessary computational bloat of generalized platforms, synthesizing the lessons learned from the aforementioned literature to provide a pragmatic, full-stack operational solution.

\subsubsection{Eradicating the Single Point of Failure and Insider Threats}
Rather than relying on probabilistic AI anomaly detection to catch insider threats, the proposed system resolves the centralized database crisis through deterministic cryptographic immutability.
\textbf{The Solution:} The project implements a custom-coded, three-phase-commit-inspired (3PC) consensus protocol (CAN\_COMMIT, VOTE\_YES, PRE\_COMMIT, ACK\_PRE, DO\_COMMIT) over raw TCP sockets. This ensures synchronous agreement, meaning a single malicious database administrator cannot unilaterally alter a patient's history. This Proof of Authority (PoA) consensus style—validated as appropriate for healthcare consortium environments by recent frameworks like BlockCare (2024)—significantly reduces the single-admin control risk of centralized databases, without the energy waste of PoW. (In the current demo network, quorum size is hard-coded and messages are not cryptographically authenticated.)

\subsubsection{Bypassing EVM Constraints with a Native C-Core}
Unlike MedRec or Ancile which suffer from Ethereum gas fees and 256-bit word limits, this project completely circumvents public network bottlenecks.
\textbf{The Solution:} The architecture executes a low-level, native C blockchain core. It enforces deterministic memory allocation by defining rigid, fixed-width C struct representations for blocks and transactions, storing them directly to disk via blockchain.dat with explicit fsync operations. This guarantees predictable, zero-cost computational performance, allowing the network to scale rapidly.

\subsubsection{Separation of Concerns: Decoupling Logic from the Ledger}
To avoid the computational bloat seen in FHIRChain and MedChain, the proposed system aggressively minimizes its on-chain footprint.
\textbf{The Solution:} The blockchain transaction struct only stores foundational metadata (patient\_id, doctor\_id, data\_hash, data\_pointer, timestamp). The heavy lifting of role-based access control (RBAC), user session management, and interface rendering is entirely decoupled from the C core and handled by the Node.js Express API and Vite React TypeScript frontend. By acting as a mathematically pristine engine of integrity rather than a bloated application server, the system achieves horizontal scalability.

\subsubsection{Deterministic Local Off-Chain Storage (Replacing IPFS Risks)}
To resolve the latency and data-loss risks of IPFS swarms (seen in BiiMED and EHRChain) and the centralization of cloud providers (seen in MeDShare), the system implements a natively managed hybrid storage architecture.
\textbf{The Solution:} When a record is uploaded, the Node.js API triggers the C core's ENCRYPT command, which executes mock envelope encryption (slated for upgrade to AES-256-GCM). Crucially, the resulting .enc file is stored in a localized offchain/records directory physically located on the node's disk. In this local prototype, this provides predictable, deterministic retrieval speeds compared to an ephemeral IPFS swarm. In a production deployment on controlled hospital infrastructure, this architecture is also compatible with HIPAA storage requirements, though formal compliance controls are outside the current prototype scope.

\subsubsection{Deterministic Cryptographic Duplicate Prevention}
The system replaces the computationally heavy semantic matching of traditional MDM frameworks highlighted by Tayal and Adapa with mathematical precision.
\textbf{The Solution:} The architecture implements a transaction hash index engineered with a pure-C Bloom filter utilizing three independent DJB2-based hash functions. This provides a constant-time O(1) pre-filtering cache. If a duplicate file hash is detected, the API instantly rejects the upload with an HTTP 409 Conflict response before it hits the consensus network. To scale this determinism to over 1 billion records without exhausting physical RAM, the project outlines a LevelDB Log-Structured Merge (LSM) tree integration, bounding memory usage to ~2 GB.

\subsubsection{Browser-Side Merkle Inclusion Verification}
A critical vulnerability in web-based blockchain dashboards is the light-client trust boundary—if the backend API is compromised, it can falsely validate tampered records.
\textbf{The Solution:} The proposed project implements browser-side Merkle inclusion verification. When verifying a record, the C core generates a full Merkle proof containing sibling hashes and directional paths. The React frontend independently recomputes the SHA-256 hash of the uploaded file via Web Crypto APIs, reconstructs the canonical leaf, and applies the proof to verify the computed root matches the block header Merkle root. This provides Merkle inclusion proof for the returned block header. Note that a fully secure light-client would additionally need to validate the block header against trusted validator signatures and a verified header chain, which is left as future work.

4.1.2 Tamper Evidence

Tamper evidence is provided by:

 SHA-256 transaction hashes, Merkle roots, previous\_hash linkage, and full chain verification.

Changing one stored block changes its hash. The next block still points to the old hash, so verification fails.

4.1.3 Duplicate Detection

The system indexes transaction hashes. If the same file hash already exists, the node can reject the record. This helps prevent replay of identical medical documents.

4.1.4 Validator Identity

Each block stores validator\_port and validator\_signature. In a production system, validator identity should be tied to a real public key, certificate, and institution identity. In the current demo, signature verification is simplified.

4.1.5 Current Signature Limitation

The current signature implementation is not cryptographically secure. sign\_data creates a string beginning with SIG\_V1\_ and includes the block hash and key path. verify\_signature now reconstructs the expected demo signature for the supplied block hash and corresponding key path rather than accepting only a prefix, but this is still a demonstration mechanism rather than real public-key cryptography. It is acceptable only for demonstrating the block signing workflow. It is not sufficient for real security.

A production version should use:

 Ed25519, ECDSA, or RSA-PSS signatures, real public/private key verification, certificate management, signed block headers for light-client validation, key rotation, revocation list, and hardware-backed private keys for validators.

4.1.6 Merkle Proof and Light-Client Trust Boundary

The current verifier can prove that a returned transaction belongs to a returned block header. The browser recomputes the file hash, reconstructs the transaction leaf, applies the left/right sibling proof, and checks the computed root against the returned Merkle root. This reduces the need to download full blocks for record inclusion checks.

However, Merkle proof verification alone does not prove that the block header belongs to the real authorized chain. A production light client must also validate the block header through trusted validator public keys, signed header chains, previous\_hash linkage, validator-set rules, and/or trusted checkpoints. Without this additional header validation, a malicious server could return a fake header and a matching fake proof.

4.1.7 Network Security

Current node communication is plain TCP. It does not use TLS. This means traffic can be observed or modified by an attacker on the network. The block verification layer can detect some invalid data, but confidentiality and authenticity of transport are not guaranteed.

A production-ready network transport layer must enforce strict confidentiality and authentication. This necessitates the deployment of Mutual TLS (mTLS) for all inter-node communication, supported by a formal Public Key Infrastructure (PKI) issuing node-specific certificates. Additionally, the network must maintain a cryptographically signed peer registry and implement robust defensive mechanisms including replay protection, strict message authentication codes, and adaptive rate limiting against denial-of-service vectors.

4.1.7 Backend Security

The API uses child\_process execution to call C binaries. This is acceptable for a controlled demo but requires hardening. Commands must be strictly controlled to avoid injection risk. In the current code, commands are mostly predefined, but future features should avoid passing raw user input into shell commands.

4.1.8 Frontend Security

The system currently uses local mock authentication across both frontend and backend. This is suitable for demonstration and local testing but not for real deployment. Production must integrate a real Identity Provider (IdP) consistently across the stack.

\subsection{Testing and Verification Status}

During the latest review, the verification commands passed successfully, including frontend linting and building, backend API JavaScript syntax checks, and core compilation via MinGW. Additionally, the core viewer correctly returns EMPTY when no central core ledger exists.

The frontend build produced only a Vite bundle-size warning, not a failure.

Important interpretation:

The core viewer returns EMPTY when no data/blockchain.dat exists in backend/core. Demo instances still contain their own chain files. Therefore, an empty central core chain is not the same as a corrupted demo chain.

Current testing gaps include the absence of API unit tests, frontend component tests, automated multi-node consensus tests, upload integration tests, and long-running network stability tests. Cryptographic signature tests are also omitted because the current signatures are mock implementations, and there is no fuzz testing for the serializer/parser.

\section{DISCUSSION AND LIMITATIONS}

\subsection{Current Weaknesses and Gaps}

5.1.1 Mock Signatures

The largest security weakness is that the signature system is not real cryptography. It demonstrates the shape of signing but does not protect against forgery.

5.1.2 Auth Model Is Demo-Level

The backend and frontend authentication have been unified around a local mock registry via the X-Mock-User-ID header. This provides a clean, zero-dependency demonstration experience without requiring external services like Supabase. However, for a production system, this must be replaced with a single, secure Identity Provider (IdP) with proper token validation, session management, and role enforcement backed by a real identity store.

5.1.3 Upload Flow Is Integrated at Demo Level

The upload controller is now fully integrated with the C core encryption commands. When a record is uploaded, the Express API calls the C core's ENCRYPT command (which implements Mock Envelope Encryption). This derives a temporary file key, encrypts it under both the patient's ID and doctor's ID, encrypts the file payload, and stores it in the demo node's offchain/records directory as a secure .enc file. The API then calls the ADD command to commit the transaction to blockchain.dat. The remaining limitation is that the cryptographic operations use a mock XOR cipher (for zero-dependency compilation on Windows) rather than standard production-grade AES-256-GCM and RSA-4096.

5.1.4 Verification UI Is Now Integrated

The Verify Record page no longer simulates verification. It uploads the file to /api/records/verify. The backend passes the file to the C viewer VERIFY\_FILE command, which recomputes the SHA-256 hash, uses the hash index to locate the transaction, and returns a proof-backed response. A MATCH response returns the block index, transaction index, hash, data pointer, patient ID, doctor ID, transaction metadata, block header fields, and Merkle proof steps. A NOT\_FOUND response returns the computed hash. The frontend recomputes the file hash and verifies the returned Merkle proof locally before displaying success.

5.1.5 Plain TCP Networking

Node communication is not encrypted. Production healthcare systems need TLS or mutual TLS.

5.1.6 Consensus Is Demo-Level

The three-phase commit inspired logic is useful but not a complete consensus protocol. It lacks formal handling for malicious validators, network partitions, leader changes, conflicting proposals, and dynamic validator sets.

5.1.7 Binary File Storage Has Portability Risks

The ledger writes C structs directly to disk. This is simple, but it can be sensitive to compiler, platform, architecture, struct layout, and time\_t size differences. A production ledger should use a canonical binary or JSON/CBOR/Protobuf format.

5.1.8 Limited Automated Tests

The repository contains test sources, but the frontend and backend do not have meaningful automated test suites. backend/api npm test is a placeholder.

5.1.9 Logs and Demo Data Are Tracked

Demo blockchain files, node logs, and binaries appear in the repository. For production-quality repository hygiene, generated artifacts should usually be excluded or separated from source.

5.1.10 Mock Hashing and Cipher Limitations

While the end-to-end encryption pipeline is now fully integrated into both web uploads and downloads via the C core's ENCRYPT/DECRYPT commands, it uses simulated cryptography (XOR-based mock ciphers) rather than standard OpenSSL cryptosystems. This is suitable for demonstrating the structural envelope flow, but does not provide cryptographically secure data protection.

5.1.11 No Real Patient Consent Model

A medical system should record patient consent, access grants, revocations, and audit trails. The current project focuses on integrity, not consent governance.

5.1.12 No Production Database Schema

A robust identity and access management system must be implemented. The chain and frontend are not fully integrated with a stable database schema for users, permissions, records, and audit metadata.

\subsection{Compliance and Ethical Considerations}

5.2.1 Privacy

The system correctly avoids putting raw medical files on-chain. This is the most important privacy-preserving decision in the architecture.

5.2.2 Data Minimization

Only hashes, pointers, and limited metadata should be stored on-chain. In future versions, patient\_id and doctor\_id should be pseudonymized or tokenized more strongly.

5.2.3 Right to Erasure

Blockchain data is immutable, so deleting on-chain data is difficult. The hybrid model helps because the medical file can be deleted off-chain while the chain retains only a hash. This is often called crypto-shredding when encryption keys or encrypted files are destroyed.

5.2.4 Consent

The current implementation does not fully model patient consent. A production medical system should record:

 consent granted, consent revoked, consent scope, who accessed a record, why access occurred, and emergency override events.

5.2.5 Auditability

The ledger and logs support auditability, but production audit logs need stronger guarantees. API logs should be append-only, protected from modification, and possibly anchored into the blockchain itself.

5.2.6 Ethical Use

A system like this should never expose raw medical data unnecessarily. It should also avoid giving a false sense of security. Blockchain protects integrity, but it does not automatically solve access control, confidentiality, consent, or clinical correctness.

\section{FUTURE WORK AND PRODUCTION ROADMAP}

\subsection{Cryptographic Hardening}

While the current prototype demonstrates the feasibility of a permissioned, tamper-evident medical ledger, production deployment requires substantial cryptographic maturation. The XOR-based mock envelope cipher must be replaced with AES-256-GCM, which provides authenticated encryption with associated data (AEAD), guaranteeing both confidentiality and ciphertext integrity for off-chain payloads. Mock validator signatures must be replaced with real asymmetric cryptography: Ed25519 for its speed and compact key size, or ECDSA P-256 for compatibility with existing healthcare PKI standards such as X.509. Block serialization must also be standardized away from raw C struct writes, which are platform-dependent, toward a stable wire format such as Protocol Buffers to ensure cross-platform reproducibility of block hashes.

\subsection{Non-Custodial Key Management for Patients and Clinicians}

A system requiring patients or doctors to memorize raw 256-bit cryptographic keys is undeployable. The production system must implement a non-custodial key management architecture across three pillars. First, private keys must be committed to device-level Hardware Secure Enclaves---such as the Apple Secure Enclave, Android Keystore, or Windows TPM---where they are physically unextractable and biometrically gated. Second, the high-entropy seed must be encoded into a BIP-39 mnemonic phrase of 12 to 24 words, or derived on-device using Argon2id from a user password, eliminating the need to handle raw cryptographic material. Third, if a patient loses their device and mnemonic, Threshold Social Recovery via Shamir's Secret Sharing (SSS) allows reconstruction: the master key is sharded across five hospital consortium authorities, and any three can reconstruct it upon physical identity verification, without any single hospital possessing the complete key.

\subsection{Network Security and Transport Layer}

The current prototype uses plain, unauthenticated TCP. A production deployment must mandate Mutual TLS (mTLS), where every validator node holds a certificate from a consortium Certificate Authority (CA), ensuring only authorized nodes participate and all consensus messages are encrypted in transit. The system also requires a formal Validator Governance framework covering node onboarding, key rotation, revocation, and configurable quorum thresholds---parameters that are currently hard-coded in the demo.

\subsection{Consensus Protocol Formalization}

The demo voting flow must be formalized into a Byzantine Fault Tolerant (BFT) protocol such as PBFT or Tendermint, providing formal safety and liveness guarantees that natively handle network partitions, malicious proposer equivocation, and automated recovery from validator failure---all essential properties for a production hospital environment.

\subsection{Scalable Storage and Indexing}

At scale, the in-memory hash maps become untenable: storing one billion records would require over 184 GB of RAM. The production architecture must migrate to a Log-Structured Merge (LSM) tree database such as LevelDB or RocksDB, whose MemTable buffering, SSTable compaction, and built-in Bloom filters would cap memory usage at approximately 2 GB while maintaining $O(\log N)$ SSD lookup performance across transaction hash, patient history, and doctor audit indexes.

\subsection{Access Control, Consent, and Compliance}

A complete clinical deployment requires granular patient consent management: the ability to grant and revoke per-doctor access, define time-bounded windows, and enable emergency override modes. Every access event must be recorded on-chain as an immutable audit transaction, satisfying HIPAA and GDPR audit trail requirements. Role-Based Access Control (RBAC) extended with Attribute-Based Access Control (ABAC) would enable expressive policies, forming the critical path toward a compliance-ready deployment.

\section{CONCLUSION}

\subsection{Summary}

This project is a strong academic and engineering prototype of a permissioned blockchain-based medical record integrity system. Its most important idea is the separation of medical data storage from integrity proof. Sensitive files remain off-chain, while hashes and metadata are stored in a tamper-evident ledger. This design aligns with healthcare privacy needs better than storing raw records directly on-chain.

The current repository demonstrates more than a theoretical blockchain. It includes a C ledger engine, a peer networking layer, a synchronization mechanism, a Node.js API bridge, and a React dashboard. This makes the project suitable for demonstration, explanation, and further development.

The project also honestly reveals the gap between prototype and production. It still needs real cryptographic signatures, trusted light-client header validation, real authentication integration, secure transport, persistent indexing, automated tests, formal validator governance, and stronger consensus rules. These are not minor details; they are essential for real healthcare deployment. However, the current implementation provides a meaningful foundation on which those improvements can be built.

The uniqueness of the work lies in its full-stack nature and its healthcare-specific architecture. It does not merely use blockchain as a buzzword. It uses blockchain for a specific property: tamper evidence. It does not place private data on-chain. It recognizes that permissioned identity is more suitable than public mining for hospitals. It uses a dashboard to make the system understandable to users and examiners.

In final evaluation, the project should be presented as a permissioned medical integrity ledger prototype with a working core, demonstrable dashboard, and clear future path toward production-grade security and compliance.
